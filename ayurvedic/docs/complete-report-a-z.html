4. Booking & consultation system

A native booking engine (no third-party calendar), with two journeys:

Direct treatment: pick treatment → choose date & slot → submit request → staff approve & assign therapist → pay online → confirmed
Consultation-first: request consultation → pick time → approve → consultation (free) → doctor clears guest → book & pay for treatment → confirmed
  • Book as a guest or signed in. A "Before you book" arrival note and policy disclaimers (same-gender therapist, non-refundable cancellation window, WhatsApp rescheduling) are shown at checkout.
  • Smart time-slot picker — dates from tomorrow onward, 30-minute slots, last slot adjusted to therapy length, with a 30-minute buffer after each booking. Only times where a same-gender therapist is genuinely free appear, so the clinic is never double-booked — and the therapist's name is never shown to the customer.
  • Group bookings — a couple or up to 6 guests in one request, each with name, gender and age; the group pays once, after all guests are approved.
  • Payment window & auto-release — an approved booking must be paid within 15 hours; a reminder email is sent, and if the window lapses the slot is automatically released and re-opened.
  • Every request appears on the front-desk, doctor and admin dashboards; any one can approve, or reject with a reason so the guest can easily re-book.

  • Five roles, each routed to its own area and protected so no one sees another's pages: Customer (account), Front Desk (console), Doctor (doctor portal), Admin (back-office), Sales Agent (partner portal).
  • Affiliate referral links (?ref=CODE) are tracked for commission attribution.

10. Payments & email

  • Payments — Billplz (FPX / online banking). Treatments are paid in full online after approval; products are paid at checkout. Payment auto-confirms the booking / order. Refunds are processed from the Billplz dashboard. Consultations are free.
  • Email — Brevo (SMTP). Sends booking & order confirmations, payment links, reminders and rejection / auto-release notices. The system is provider-agnostic, so the email provider can be swapped without code changes.

12. Why it is secure

Security is layered — a request has to pass several independent checks before it can read or change anything. These are the protections actually built into the platform:

Managed, industry-standard sign-in

Accounts and sessions are handled by Supabase Auth — a managed service used by thousands of companies — over secure, server-side session cookies. Passwords are never stored by us in readable form. Sign-in supports email & password, one-time email codes (OTP), and "Continue with Google". Signups are validated (email format, minimum 8-character password) before an account is created.

Two layers of role protection

Every staff and customer area is gated twice: first at the front door (middleware checks your role on every request and redirects you to your own portal), and again on the server before any sensitive action runs. An Admin URL simply cannot be opened by a customer, doctor or agent — the five roles (customer, front desk, doctor, admin, sales agent) are kept strictly apart.

Database-level Row-Level Security (RLS)

Even if application code were bypassed, the database itself enforces the rules. Postgres RLS policies ensure a customer can only ever read their own appointments, orders and messages, an agent can only see their marketplace orders (and can't approve their own), and only admins can change protected records. Full-access "service-role" keys are used only on the server, after the role is verified — never in the browser.

Cryptographically verified payments

Payment confirmations from Billplz are verified with an HMAC-SHA256 X-Signature using a secret only the server knows, compared in a timing-safe way (resistant to timing attacks). A booking is marked paid only after this check passes. The amount is always computed on the server from the database — never trusted from the browser — so prices can't be tampered with. Confirmation is idempotent (a replayed callback can't double-charge or double-confirm). Incoming Cal.com webhooks are verified the same way.

Protected links, secrets & audit trail

Guest booking links are protected by a private signed token (and the system refuses to run in production without its signing secret set). All secret keys (service role, Billplz, email) live only in server environment variables and are kept out of the code repository via .gitignore. Sensitive staff actions and every order status change are written to an audit log (who did what, when) for accountability, and customer health data is treated as PDPA-protected.

Recommended hardening before public launch: turn customer email-OTP back on, add explicit security response headers (CSP / HSTS) at the hosting layer, and verify the clinic domain in Brevo for best email delivery — see Section 15.

13. Why it is fast

Speed is designed in, not bolted on. The site is built on modern rendering techniques that send the browser the least work possible:

TechniqueWhat it means for speed
Next.js 14 server componentsPages are rendered on the server and sent as ready-made HTML, so very little JavaScript ships to the phone — pages appear quickly even on mobile data.
Cached & pre-built pages (ISR)Home, About, Contact and Blog are served from a cache and quietly refreshed, so most visitors get an near-instant page. Every treatment and blog page is pre-generated.
Global image CDN + optimisationPhotos are delivered from Sanity's and Supabase's global CDNs in modern formats and correct sizes, so images load fast without slowing the page.
Vercel edge hostingThe site is served from Vercel's global edge network with automatic deployments — close to the user, always on.
Optimised fontsFonts load with a "swap" strategy and are automatically subset, so text is readable immediately with no invisible-text flash.
Efficient database queriesAdmin lists use pagination and indexed columns, so large tables (orders, customers, appointments) stay quick to load and filter.
Lean styling & code-splittingTailwind ships only the CSS actually used, and each page loads only the code it needs; animations run on the client without blocking content.
Automatic background jobsHousekeeping such as releasing unpaid slots runs on a scheduled server cron — never on the visitor's device.

The result: fast first paint, strong mobile performance, and search-engine-friendly pages (server-rendered HTML with structured data).

14. What is "archived"

"Archived" means fully built but intentionally switched off for the current clinic-first (bookings-only) launch. Nothing is deleted — it can be turned on later without rebuilding. There are three kinds of "archive" in the project:

a) Phase-2 commerce, hidden behind one switch

The full online shop and partner programme are complete but hidden by a single feature flag (COMMERCE_ENABLED). While it's off, the clinic runs on bookings only, and these are removed from the menus and dashboards — yet remain ready to go live instantly:

Customer-facing (archived):

  • Product shop & product pages
  • Home-page shop & promo sections
  • Account: Orders, Wishlist, Promo wallet, Reviews, Addresses
  • "Brand Partner" navigation link

Admin-facing (archived):

  • Products, Inventory, Orders
  • Marketplace & Wholesale orders
  • Brand Partners & Agent submissions
  • Vouchers & Finance; shop KPIs on the dashboard

These routes still exist and work — they are simply not shown in the sidebars until commerce is switched on.

b) "Archived" product status (soft-delete)

Within the product catalogue, each product can be Active, Draft or Archived. Archiving a product hides it from the shop without deleting it or losing its history — a safe way to retire an item and bring it back later.

c) Design & planning archive (internal)

Early prototypes, mockup variants (business-card, hero and directory explorations) and the original planning documents are kept in the project's /mockups, /prototypes and docs folders for reference — not part of the live site, but retained so the design history isn't lost.
